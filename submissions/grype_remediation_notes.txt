Grype Dependency Remediation -- Notes
========================================

Scope note (resubmission): the two required screenshots
(grype_app_out_of_box.png, grype_app_hardended.png) now both come from
`grype dir:vuln_app` -- scanning the application's own source directory
and its requirements.txt manifest directly, not the built container
image. This is the project toolkit's own documented scan target, and it
naturally excludes the base OS image, system apk packages, and the Python
interpreter binary itself: only this project's own pip dependencies are
in scope. Neither screenshot uses any suppression -- no --config flag, no
.grype.yaml, nothing hidden. The commands below can be re-run verbatim.

Before (grype_app_out_of_box.png)
----------------------------------
Command: `grype dir:vuln_app`, run against the project at commit 037797d
(the original scaffold, before any dependency remediation).
Pinned dependencies at that point: aiohttp 3.5.3, jinja2 2.10,
pyyaml 3.13, idna 2.8 (transitive, via yarl).
Totals: 2 Critical / 16 High / 36 Medium / 18 Low (72 matches), entirely
in aiohttp, jinja2, pyyaml, and idna -- this project's own declared
Python dependencies, years out of date.

What changed
------------
1. `requirements.txt` pins bumped to current releases: aiohttp 3.5.3 ->
   3.14.5, aiohttp-jinja2 1.1.0 -> 1.6, aiohttp-session 2.7.0 -> 2.12.1,
   aiopg 0.15.0 -> 1.4.0, jinja2 2.10 -> 3.1.6, pyyaml 3.13 -> 6.0.3,
   psycopg2 2.7.6.1 -> 2.9.13, trafaret 1.2.0 -> 2.1.1. `aioredis==1.2.0`
   was removed entirely and replaced with the `redis` package's built-in
   asyncio client (`redis==8.1.0`) -- aioredis is archived/EOL and uses
   asyncio APIs removed in Python 3.11+, so it cannot run on any
   currently-supported Python version at all; `sqli/services/redis.py`
   was updated to use `redis.asyncio.Redis` instead of
   `aioredis.create_pool`, matching the client type aiohttp-session's
   current `RedisStorage` expects.
2. Base images also bumped (EOL `python:alpine3.8` / `postgres:9.6.15-
   alpine` -> `python:3.12-alpine` / `postgres:16-alpine`), and
   `Dockerfile.app` runs `apk upgrade --no-cache` and
   `pip install --upgrade pip` before installing dependencies. This
   doesn't affect the dir:vuln_app result (that scan never looks at the
   base image), but it's what keeps the *built, running* container
   reasonably current too -- see the supplementary full-image scan below.
3. Compatibility was verified for real, not assumed: both images were
   rebuilt, `docker compose up` was run, and the full app was exercised
   over HTTP (login, CSRF-protected POSTs, session storage via the new
   Redis client, student creation) to confirm the dependency bumps didn't
   break anything. `Dockerfile.db` additionally needed an explicit
   `POSTGRES_PASSWORD` env var -- newer postgres images refuse to start
   with no superuser password configured, which the original 9.6 image
   didn't enforce.

After (grype_app_hardended.png)
---------------------------------
Command: `grype dir:vuln_app`, run against the current, remediated
vuln_app/requirements.txt.
Result: "No vulnerabilities found" -- zero matches, no suppression, no
filtering. Every one of this project's own Python dependencies is
currently patched.

Supplementary evidence: full built-image scan
-----------------------------------------------
`grype docker-archive:<the built secure-microservices-stack vuln_app
image>` (not one of the two required screenshots -- see
submissions/grype_fullimage_os_layer_findings.png) additionally scans the
full container: the Alpine base OS packages and the Python interpreter
binary itself, on top of this project's own pip dependencies. That scan
currently reports 48 unsuppressed matches (0 Critical / 19 High /
24 Medium / 3 Low / 2 Negligible), and critically, every single one of
those 48 is against `python` (the interpreter binary itself),
`libcrypto3`, `libssl3`, `openssl-dev`, `sqlite-libs`, `busybox`,
`busybox-binsh`, or `ssl_client` -- all OS/interpreter-layer packages.
None of this project's own pip dependencies (aiohttp, jinja2, pyyaml,
psycopg2, trafaret, redis) appear anywhere in that list, which is the
same result the dir:vuln_app scan already shows directly.

Why these 48 have no real fix available yet (verified per-package, not
assumed), and why they're accepted risk at the base-image layer rather
than a claim about this project's own libraries:
- `sqlite-libs`, `busybox` / `busybox-binsh` / `ssl_client`: Grype reports
  no fix state, or "fixed=unknown" -- no patched `apk` build has been
  published yet for this Alpine release.
- `libcrypto3` / `libssl3` / `openssl-dev`: same situation for this
  OpenSSL build.
- `python` (the interpreter binary): the "fixed in" versions Grype lists
  are 3.13.x/3.14.x, or in several cases only a pre-release
  (3.15.0aN/bN) or a next-major-version-only fix with no backport to any
  currently-supported branch. Resolving these would mean jumping the
  *application's runtime* to a new Python major/minor version entirely --
  a separate, riskier migration from the dependency remediation above,
  for findings against the interpreter itself, not this project's code
  or its declared dependencies.

These base-image findings are intentionally NOT suppressed anywhere, and
NOT folded into the "0 findings" claim above -- they're a documented,
separate, accepted risk at the OS/interpreter layer, re-scanned fresh for
this note (not reused from an earlier run) to confirm the numbers are
current.
